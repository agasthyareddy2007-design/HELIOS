HELIOS Architecture

Technical reference for the weather-model blending and post-processing platform

System Overview

HELIOS is an ensemble blending and post-processing system that combines predictions from multiple Numerical Weather Prediction (NWP) models to produce more accurate and calibrated forecasts. It is NOT an independent NWP model.

⚠️ Important

Each NWP model has different APIs, archive availability, licensing, resolution, and access mechanisms. An abstraction layer normalizes all sources into a common HELIOS format.

ML Competitors

HELIOS evaluates three machine learning approaches, each with distinct strengths:

1. Kernel Regression

Similarity-Based

Weights historical situations based on similarity to current conditions. Factors include:

  • Temporal recency - More recent situations have higher influence
  • Geographic similarity - Similar locations and topography
  • Season - Similar time of year and solar forcing
  • Atmospheric conditions - Similar weather regimes
  • NWP model disagreement - Ensemble spread and uncertainty

Key Concept: Recent + similar atmospheric situation → higher influence; Old + dissimilar → lower influence; Old + highly similar atmospheric regime → can still be useful

2. XGBoost

Gradient Boosting

Gradient boosting for tabular weather features. Input features include:

  • NWP forecast variables from all models
  • Ensemble spread and disagreement metrics
  • Lead time, forecast issue time, valid time
  • Seasonal indicators (month, season, hour)
  • Location (latitude, longitude)
  • Recent observed weather and ERA5 context
  • NASA POWER auxiliary data

3. MLP (Multi-Layer Perceptron)

Neural Network

Neural network approach using PyTorch. Receives the same scientifically valid feature set as XGBoost for meaningful comparison.

Hardware: NVIDIA RTX 5080 for training and inference

Baselines for Comparison

HELIOS must prove it improves upon:

  • Individual NWP forecasts - Raw model outputs

  • Persistence/climatology - Where appropriate

Forecast Verification

🔒 Critical Principle

Never allow future observations to leak into forecasts.

A forecast issued at 2026-09-05 00:00 UTC for 2026-09-06 12:00 UTC must be evaluated against the observation that becomes available at/after the valid time.

Verification Records

Each forecast is tracked with:

Field Description
forecast_issue_time When the forecast was generated
forecast_valid_time The time the forecast is for
lead_time Hours between issue and valid time
model NWP model or HELIOS version
location Geographic coordinates
forecast_value Predicted value
observed_value Actual observed value (after valid time)
error forecast - observed
absolute_error |forecast - observed|
squared_error (forecast - observed)²

Metrics Breakdown

Evaluation is stratified by:

  • Weather variable - Temperature, precipitation, wind, etc.
  • Lead time - 0-6h, 6-24h, 24-72h, 72-168h, etc.
  • Location/region - Geographic zones
  • Season - Summer, winter, monsoon, etc.
  • Model - Individual NWP models vs HELIOS

Appropriate Metrics:

  • Continuous variables: MAE, RMSE, bias (mean error)
  • Probabilistic predictions: Brier score, calibration, reliability

Model Versioning & Checkpointing

Each trained HELIOS version is independently identifiable:

helios-0.1 → helios-0.2 → helios-0.3

Checkpoint Contents

  • Model files (weights, architecture)
  • Model version identifier
  • Feature configuration and preprocessing parameters
  • Normalization/scaling parameters
  • Hyperparameters
  • Training period (start/end dates)
  • Data source versions
  • Evaluation metrics (MAE, RMSE, bias by lead time/region)
  • Training timestamp
  • Git commit/version reference
💾 Rollback Capability

Do not delete old checkpoints automatically. We need model rollback capability if a new version underperforms.

Progressive Dataset Expansion: 1 year → 2 years → 3 years → 5 years → more

⚠️ Storage Rule

Only trained models and essential metadata remain permanently. Historical training data is temporary and deleted after checkpoint verification.

Database Schema

Database: PostgreSQL 16 (independent from any Aether database)

Core Entities

  • locations - Geographic locations and metadata
  • nwp_models - NWP model configurations and versions
  • nwp_runs - Forecast model runs (initialization times)
  • nwp_forecasts - Individual NWP predictions
  • observations - Observed weather data
  • forecast_verification - Forecast vs observation comparisons
  • helios_predictions - HELIOS blended forecasts
  • model_versions - HELIOS model checkpoint metadata
  • model_metrics - Evaluation metrics by version
  • training_runs - Training session records

Purpose: PostgreSQL contains structured application data, metadata, forecast records, observations, verification results, model versions, and metrics. Raw scientific weather data uses GRIB/NetCDF/Zarr formats.
